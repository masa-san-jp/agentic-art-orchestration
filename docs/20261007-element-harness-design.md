# 要素単位ハーネス設計（element harness）v1

作成: 2026-10-07。オーナー決定に基づく再設計の正本。実装はこの文書の段階順に行い、各段階の完了は「実 run の出力をオーナーが確認して良しとしたこと」で判定する。テスト合格や件数の増加だけでは完了としない。

## 1. なぜ作り直すか

2026-10-07 の実 run（LIVE-20261007-1）で、次のことが確認された。

- テーマを決めるまでの工程に推論が一つも無く、要素の組み合わせ（自己 × 美術史 × 市場）を機械的に全部作り、形式検査を通ったものからハッシュ順で1件を選び、値を「∩」でつないだ文字列を研究の問いにしていた。要素どうしの関係は一度も考えられていない。空の要素は「無し」として問いに混入した。
- 研究（research）の9作業は、1回の推論でその作業のファイルを全部書かせ、検査に落ちると作業ごと捨てて書き直す作りだった。小さなモデルでは成立しない。作業者には命題すら渡っていなかった。
- 制作の要点（主張・反対者・仕掛けなど）は「未記入」のままでも検査を通った。
- ヒアリングは、下流で使われない項目を、空いている欄のアルファベット順で選んだ定型の質問だった。答えても何にも効かない。

## 2. 設計原則（オーナー決定 2026-10-07）

1. **決定論で処理できる部分は、推論を使わずプログラムで処理する。** 並べ替え、数え上げ、結線、表引き、件数、日付、ID、hash、転記、描画はすべてプログラムが行う。
2. **推論は1要素1推論にする。** 1回の推論で出させるのは、1つの値（1文、1つの分類、はい/いいえ＋理由1文など）だけ。複数の要件を1回で満たさせない。
3. **一般的なローカルモデルでも答えられる大きさにする。** 1件の依頼には、短い指示、その要素に必要な最小限の材料、返す形の決まりだけを入れる。
4. **出た値はプログラムで確かめ、だめならその要素だけをやり直す。** 理由を添えて同じ要素をもう一度依頼する。候補を捨てて選び直したり、空のまま（「無し」）次へ進めたりしない。
5. **自己モデルは全体を材料にする。** 一部の項目に絞らない。
6. **答えるのは誰でもよい。** Claude Code などクラウドのエージェントでも、ローカルのエージェントでもよく、ハーネスは区別しない。ウェブ検索も、ハーネスが依頼を出し、利用中のエージェントが実行して結果を返してよい。

## 3. 共通の仕組み: 1件の依頼 → 1つの答え → 確認 → やり直し

### 3.1 依頼（`element-request/v1`）

ハーネスは、次に必要な要素を1件ずつ依頼として出す。

```json
{
  "contract_version": "element-request/v1",
  "run_id": "<run>",
  "element_id": "A6.central-question",
  "attempt": 1,
  "instruction": "次の3つの材料が重なるところを、1つの問いの文にしてください。",
  "inputs": {"self": "…", "art_history": "…", "market": "…"},
  "answer_format": {"type": "text", "max_chars": 120},
  "checks": ["ends_with_question", "contains_terms:self,art_history,market", "forbidden:∩,無し,未記入"],
  "previous_failure": null
}
```

- `instruction` は1〜2文。`inputs` はその要素に必要なものだけ。
- `answer_format` は `text`（文字数の上限付き）、`choice`（列挙からの1つ）、`boolean_with_reason`、`url` のいずれか。
- 2回目以降は `previous_failure` に、落ちた検査の名前と短い理由が入る。

### 3.2 答え（`element-answer/v1`）

```json
{"contract_version": "element-answer/v1", "run_id": "<run>", "element_id": "A6.central-question", "attempt": 1, "value": "…"}
```

### 3.3 確認とやり直し

- 確認はすべてプログラム（`checks` の各項目）。例: 空でない、文字数、問いの形、必須語を含む、禁止語を含まない、列挙に含まれる、参照する ID・URL が実在する、取得した本文と完全一致する、他の答えと似すぎていない。
- 落ちたら、その要素だけを `attempt` を増やして再依頼する。上限（既定 5 回）を超えたら、その run は `BLOCKED` で止まり、要素名と最後に落ちた検査を返す。空の値で先へ進めることはしない。

### 3.4 答え方（どのエージェントでも同じ）

- `tools/run.py` は、次の依頼を `next_action`（`kind: element`）として返して止まる。
- エージェントは依頼を読み、値を作り、`tools/element.py answer --run-id <run> --state-root <root>` に標準入力で答えを渡す。ハーネスが確認し、通れば次の依頼、落ちれば同じ要素の再依頼を返す。
- ローカルモデル用の adapter（stdin に依頼1件、stdout に答え1件）でも、同じ依頼を自動で回せる。

### 3.5 検索の依頼（`search-request/v1`）

- 検索が要る工程では、ハーネスが「この言葉で検索し、上位 N 件の URL・題名・取得した本文を返す」依頼を出す。
- 実行は利用中のエージェントに任せてよい（ハーネスが検索の仕組みを持つ必要はない）。返ってきた URL と本文は、ハーネスが hash を取って台帳に登録する。以後の「根拠の抜き書き」は、この本文との完全一致で確かめる。

## 4. 段階 A: テーマを決めるまで（orchestration ＋ self-model-notes）

| 順 | 種類 | 内容 | 確認 |
|---|---|---|---|
| A1 | 推論 | 本人の記録（Event）から、主張・緊張・繰り返しのパターンを1件ずつ作る（self-model-notes の育成） | 参照する Event が実在する。パターンは2件以上の Event に出現することをプログラムで数える |
| A2 | プログラム | signal を書き出して集める。空の要素は組み合わせに入れない | — |
| A3 | 推論 | 本人の素材1件から、「どんな操作・状態か」を表す短い語を1つずつ出す（例: 決定の先送り） | 語の長さ、本人の素材の語と重複しすぎない |
| A4 | プログラム | A3 の語と、美術史（手法・関係）と市場（トレンドの中身）の本文を照合して、候補を数件ずつに絞る | — |
| A5 | 推論 | 絞った組ごとに「つながるか（はい/いいえ）＋理由1文」 | 理由が両方の出典の語を含む |
| A6 | プログラム | つながりのある組から、テーマに使う組を選ぶ（理由の有無と出典の強さで並べる） | — |
| A7 | 推論 | 中心の問いを1文にする | 3つの要素の語を含む、問いの形、禁止語なし、120字以内 |

ヒアリング:

- 下流で実際に使う項目（緊張、繰り返しのパターンなど）の不足を優先して聞く。
- 質問は、本人の最近の実際の出来事を手がかりにした具体的な問いにする。質問文そのものも1要素1推論（材料: 出来事1件と、埋めたい項目1つ）で作り、確認する。
- 質問と一緒に「答えると何に効くか」を1文で示す。答えは A1 で主張やパターンになり、次の run から使われる。

## 5. 段階 B: 調査（agentic-art-research）

- プログラム: 問いの数・予算・資料の上限、検索の実行・取得・hash・台帳・重複除去・停止判定、主張の組の列挙、支持/対立の組み立て、自己反復の計算、権利の表引き、完了判定。
- 推論（1つずつ）: 問いの文 → 検索の言葉（問い×方針ごと）→ 資料ごとの関係判定 → 根拠の抜き書き（本文と完全一致）→ 観察 → 主張文 → 主張の種類 → 主張の組ごとの関係 → 洞察 → 判断の問い → 選択肢（1つずつ）→ 採用 → 不採用の理由 → 先行作品との違い（台帳に実在する URL のみ）。
- 作業者への依頼は「1回で1つの値」に変え、ファイルを組み立てて書くのはプログラム側に移す。

## 6. 段階 C: 作品の中身（research → production の要点）

- 推論（1つずつ）: 作品案の各項目（命題、核の問い、体験、構成要素、鑑賞者の行為、素材と振る舞い、飛躍、作り方の段取り…）→ 要点（出会いの3場面、最初の数秒、30秒後、3分後、主張、誰が反対するか、何を否定するか、語らずに見せるもの、仕掛け、技術を外すと成り立たないか）。
- 「技術を外しても地味になるだけ」と判定されたら、仕掛けの要素だけを再依頼する。案は捨てない。
- プログラム: 作品案の比較と推薦、要点のうち調査から転記できるもの（なぜ今か、先行作品の参照、自己反復の評価、読んだ資料、未決事項）。「未記入」は全項目で拒否する。

## 7. 段階 D: 制作プラン（agentic-art-production）

- プログラム: 工程・日程・予算・結線・実行可能性の判定・試作の描画（現行の `build_plan.py` と `actionability` を使う）。
- 推論（1つずつ）: 仕様の値（寸法・素材など）→ 作業ごとの手順文 → 完了の確かめ方 → 不確実性の確かめ方。`actionability` の判定結果を、要素ごとの確認とやり直しに使う。

## 8. 進め方と完了の基準

1. 共通の仕組み（3章）を orchestration に作る。偽の答え手（fake）でも全段階を回せるようにし、仕組みのテストを持つ。
2. 段階 A とヒアリングを載せ替える。実 run で、問いの文とヒアリングの質問をオーナーが確認して良しとしたら完了。
3. 段階 B、C、D を同じ仕組みへ順に載せ替える。各段階とも、実 run の出力をオーナーが確認して完了。
4. 置き換え前の経路は、置き換えが完了した段階から順に外す。

## 9. この文書で決めたこと（オーナー決定 2026-10-07）

- ウェブ検索: 行ってよい。ハーネスを利用するエージェントに任せてもよい。
- 想定する答え手: 主に Claude Code などクラウドのエージェント。ローカルのエージェントも想定し、一般的なローカルモデルの推論能力で答えられる大きさにする。
- 順番: 合理的な順で進める（本章 8）。
