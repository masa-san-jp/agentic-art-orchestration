## 0. 結論を先に

- **プログラムには「どれが関係あるか」を判定する正当な手がかりがない。** 字面の一致（#283）は全件0点、閉じた操作語彙とタグ（#284）は同じ操作の一致0件・関係で広げても弱い4件だった。意味のあったつながり（「言語化できるまで確定を避ける」⇔ 抽象表現主義の「制作過程の中で決める」）は、**対比**であり、字面にも操作の表にも現れない。
- そこで、プログラムは「関係の強さで並べる」ことをやめ、**全候補を公平に・決まった順で推論に見せる係**に徹する。関係の判定はすべて推論が行う。
- 推論は小さく分ける: (1) 8件の短い「カード」から1つ選ぶ（または「なし」）、(2) 選ばれたもの同士の勝ち抜き、(3) 勝者について「関係の種類」を閉じた一覧から選ぶ → 根拠の抜き書き（一字一句一致をプログラムで確認）→ つながりの一文 → その文がその種類の関係として読めるかの確かめ、(4) 三者の重なりの一文 → 中心の問い。
- 自己の素材は「自己モデルの記録1件（主張またはパターン1件）」。全記録を順番に使い切る回し方をプログラムで決める。
- 操作語彙・タグは「照合の鍵」としては使わない。タグの根拠抜き書き（一字一句一致済み）は**カードの文の材料**として活かす。操作どうしの関係表（補い合う・対比、72件）は段階 A では使わない。
- 1 run の推論回数は、今のデータ（美術史 179 件・市場 65 件）で **最良 約44回／典型 約50回／再試行なしの最悪 約75回**。上限は 120 回で、超えたら `BLOCKED`（理由と内訳つき）。

| 中間案（不採用の stash） | タグで並べ、k件ずつ はい/いいえ、はいが無ければ窓を広げる | 実験 run（L284-r2）: 美術 5 件中「はい」2、市場 15 件中「はい」1 | 「はい」の1件は オートマティスム「あらかじめ主題を決めずに始める」を「決定を保留する点で対応」と判定 ― 実際は**逆向き**の態度を「同じ」に潰している。はい/いいえ では関係の向きが消える。市場の「はい」は「費用」と「対価」の言葉の近さによるもの |

ここから導いた設計上の判断:

1. **並べ替えの根拠をプログラムに持たせない。** 持たせると、早く打ち切るほどその並び（＝根拠のない並び）が結果を決める。並びは「偏りのない決まった順」（ハッシュ順）にして、全件を見る。
2. **関係には向きがある。** 「同じ」「逆」「答え」「背景」を閉じた一覧から選ばせ、はい/いいえ を使わない。
3. **判定の根拠はカードの文の一字一句一致で確かめる。** 字面の照合は「選ぶ」ためではなく「答えが本文に基づくか」を確かめるためだけに使う。
4. **小さなモデルが読める大きさの「カード」を作る。** 本文全体（最大 2400 字、引用・出典のメモ混じり）をそのまま見せない。

## 3. 自己の素材

### 3.1 単位: 「自己モデルの記録1件」

- self-model-notes の書き出しは、本人が確認した **主張（Claim）1件 または パターン（Pattern）1件** が 1 signal になっている（`build_signal_export`）。その文は、tensions / recurring_patterns / seeks / avoids / protects / states / traits のどれか1つの欄に入り、条件（context-bound の場合）は contexts 欄に別の文字列として入る。
- 今の実装（`materials()`）は「signal × 欄 × 文字列」を1素材にしているため、**条件の文字列（場面の断片）が単独の素材になってしまう**。これをやめる。
- 新しい単位 = **signal 1件**。中身は次の3つで、すべてプログラムが組み立てる。

```
欄の名前（固定表で日本語に置き換え）: 引っ張り合っていること
文: 概念と表現の対応が自分の中で言語化できていない間は、費用の確定を先に進めることを避ける可能性がある
条件: （context-bound の主張なら、その条件の文。なければこの行を出さない）
```

欄の名前の固定表: tensions=引っ張り合っていること、recurring_patterns=繰り返し出る形、seeks=求めていること、avoids=避けていること、protects=守っていること、states=いまの状態、traits=ふだんの傾向。
（欄の名前の英語や self-model の専門語は、推論への入力に出さない。）

「抜き書き」の確認（A5）は **文の行だけ** を相手にする（欄の名前や条件の行から抜いても通さない）。

### 3.2 1 run で1件を選ぶ規則（すべてプログラム）

1. 候補 = 同意済み（`export_permitted: true`、`consent_scope` あり）で、文が空でない self signal の全件。欄で絞らない（原則4）。
2. 過去の run で「素材として使われた回数」が最も少ないものを選ぶ。回数は、段階 A を最後まで進めた run と、`NO_PICK` / `NO_CONFIRMED_LINK`（7.4）で終わった run の両方で数える（途中で止まった run は数えない）。
3. 同数なら、**欄ごとの使用回数の合計が少ない欄** に属するものを選ぶ（自己モデルの全欄に順に回すため）。
4. まだ同数なら、`sha256(signal_id + ":" + 使用回数)` の小さい順。アルファベット順を使わない。
5. オーナーが明示的に指定した場合（`--self-signal <id>`）はそれを使い、選び方を `owner-pinned` と記録する。存在しない ID なら `BLOCKED: SELF_SIGNAL_NOT_FOUND`。
6. 新しく育った記録は使用回数 0 なので、次の run ですぐ使われる。

今の `intent`（意図の文字列との字面の重なりで素材を選ぶ）は、#283 で字面照合が当てにならないと分かったので廃止し、5 の明示指定に置き換える（オーナー判断 12-④）。

### 3.3 自己モデルが空・足りないとき

| 状態 | 結果 |
|---|---|
| self の書き出しがない、または同意なし | `BLOCKED: SELF_EXPORT_NOT_PERMITTED`。先へ進めない |
| 同意はあるが記録が0件 | `BLOCKED: SELF_MODEL_EMPTY`。次の操作としてヒアリング（self-model-notes の `SEED_REQUIRED`）を中継する（8.4） |
| 記録が1件だけ（今の実データ） | 動く。ただし毎回同じ素材になる。2回目以降は窓の組み方（ハッシュの種に使用回数を含む）と、直近に採用した項目の除外（4.3）で、美術史・市場の側が変わる。素材の幅を増やすにはヒアリングでの育成が必要、と run の報告に書く |

空の素材や「無し」で先へ進むことはない。

## 4. 候補の出し方（美術史・市場）

### 4.1 カード

推論に見せる候補は、本文そのものではなく、プログラムが組み立てた短い **カード** にする。

```
<名前>（<時代>・<地域>）：<抜き書き1> / <抜き書き2>
```

- 名前・時代・地域・市場の段階（伸びている／出始め／ピーク）は、書き出しの欄から**プログラムが**入れる。
- 抜き書きは、各 KB の本文から**一字一句そのまま**取った部分（12〜120字、最大2つ）。カード全体は 420 バイト以内。
- 抜き書きをどこから取るかは、各 KB リポジトリ側で **1回だけ推論で決めて保存** する（4.2）。段階 A の run ごとには推論しない。
- 段階 A は run の開始時に、抜き書きが「固定した commit の本文（git の blob）に一字一句含まれること」と blob の sha256 を **プログラムで確かめる**（今の `theme_sources.py` の blob 読み取りを流用）。一致しなければ、その項目は除外ではなく `BLOCKED: CARD_SOURCE_MISMATCH`（KB 側の書き出しの不整合なので、黙って捨てない）。
- 改行の扱い: 日本語の間の改行は詰め、英字の間の改行は空白1つにする。引用記号 `>`、Markdown のリンク記法、URL、`P571` のような ID は表示前に取り除く。この規則は固定で、抜き書きの確認も同じ規則を通した後の文字列で行う。

### 4.2 カードの抜き書きの作り方（KB リポジトリ側、1回だけ）

**美術史（art-history-notes）**

- 今の 185 項目のうち、本文もタグもない項目が 6 件（ルネサンス、ゴシック美術、ロココ、新古典主義、バガン美術、安堅派）。これらはカードを作れないので段階 A の候補に入らない。数と ID を run の記録に残し、KB の不足として art-history 側の作業に回す。名前だけで埋めることはしない。
- タグを持つ 111 項目は、タグの根拠抜き書き（#284 で一字一句一致を確認済み、`operation-tags.json` / `operation-tag-additions.json`）をそのまま抜き書きとして使う。追加の推論はいらない。
- タグのない 68 項目は、1項目につき1要素の推論で抜き書きを作る。

```json
{"element_id": "K1.card.movement/gutai.1",
 "instruction": "この本文から、この美術がどんな作り方・考え方をするかを最もよく表す部分を、一字も変えずに抜き書きしてください。",
 "inputs": {"body": "<定義と範囲の節。3000バイト以内に段落単位で切ったもの>"},
 "answer_format": {"type": "text", "min_chars": 12, "max_chars": 120},
 "checks": ["exact_input_excerpt:body", "no_reference_tokens"]}
```

  例（具体美術協会）: 本文の中から「具体美術に於ては人間精神と物質とが対立したまま、握手している」が抜き書きの候補になる（決定論の「最初の文」規則では「1954年8月頃、…結成された美術家集団」になり、作り方が分からない）。2つ目の抜き書きは別要素で「もう一箇所（なければ『これ以上なし』）」。
- 保存形式はタグと同じ（本文の sha256、要素の履歴、受理値の sha256）。本文が変わった項目だけやり直す。
- 書き出し（`export_signals.py`）に `card: [{text, source_locator, source_sha256}]` を加える。`operation_id` は記録として残すが、段階 A の推論には渡さない（4.5）。

**市場（marketing-trends-notes）**

- 65 件すべてに「見出している未来」と「足元の根拠」の節がある。ただし最初の文を決まった規則で取ると、「**未確認**: …」や「〇〇社は…と主張している」という出典の説明が入る項目がある（確認: 「国内BtoC-ECの拡大」「介護サービス利用の拡大」など）。
- そこで美術史と同じく、1件1要素で「この動きが何に向かっているかを最もよく表す部分」を抜き書きする（対象の本文は「見出している未来」と「足元の根拠」の節）。本文が変わった件だけやり直す（市場は毎月見直されるので、変わるのは主に見直された件）。
- 書き出しに `label_ja` と `card` を加える（今は `statement` の決まり文句「…は stage=growing として記録されている」から名前を切り出すしかない）。

### 4.3 候補にする条件（プログラム）

- 美術史: 検証済み、または出典付きの草案（今の条件を維持）、鮮度が current、カードがある。
- 市場: 鮮度が current、`expires_at` が run の基準時刻より後、カードがある。今のデータでは 65 件中 15 件が 10/14〜10/16 に期限切れになる。
- **直近 3 回の run で採用された項目は外す**（領域ごと）。同じ有名な運動ばかりに寄るのを防ぐため。外した ID は記録する。（既定値 3。オーナー判断 12-②）
- どちらかの領域で候補が 0 件なら、`BLOCKED: ART_NO_ELIGIBLE_CARDS` / `MARKET_NO_ELIGIBLE_CARDS`。除外の内訳（期限切れ n 件、カードなし n 件、直近採用 n 件）を添える。#284 のように別の原因の文言を出さない。

### 4.4 窓と全件の見せ方（プログラム）

- 候補を `sha256(素材の signal_id + ":" + 使用回数 + ":" + 項目 ID)` の小さい順に並べ、先頭から **8件ずつ** の窓に分ける。並びは素材ごと・回ごとに変わるが、同じ入力なら必ず同じになる。
- 8件にした理由: 今のカードで1窓の入力は最大 2.4KB（美術）／2.9KB（市場）。依頼の上限 4096 バイトに収まり、小さなモデルでも一度に読める量に抑えられる。万一 4096 バイトを超える窓があれば、プログラムがその窓を前後に割る（件数は減るが全件は見る）。
- **全件を見る**（既定）。今のデータで美術 179 件 → 23 窓、市場 65 件 → 9 窓。途中で打ち切る設定も用意できるが、既定にはしない（理由と費用はオーナー判断 12-①）。

### 4.5 操作語彙・タグ・関係表の扱い

| もの | 扱い | 理由 |
|---|---|---|
| A3 操作語（自由記述・選択とも） | **廃止** | 照合の鍵として使う先がなくなる。素材の文は短い（今の素材で 49 字）ので、関係の判定には素材の文そのものを渡す方が情報が落ちない |
| 操作語彙 36 語（`operation-vocabulary.json`） | art-history 側に残す。段階 A の推論には渡さない | タグの記録の意味を保つため。推論に「身振りを残す」などの名札を見せると、その名札で判断が誘導される（#284 の `defer` だけに頼った失敗と同じ形） |
| 項目ごとのタグ（根拠の抜き書き） | **カードの抜き書きとして使う** | 一字一句一致を確認済みで、その項目の「作り方」を表す一番良い文になっている（例: コンセプチュアル・アートの "all of the planning and decisions are made beforehand…" は、書き出しの content には入っていない） |
| 操作どうしの関係表（補い合う・対比、72件） | **段階 A では使わない。** main には入れない | 操作の名前どうしで決めた関係は、実際の素材とカードの文を見ていない。必要だった「対比」は、A5 で素材とカードの組ごとに「逆」として直接判定する |
| 字面照合（#283 の `content_matches` など） | **廃止** | 選ぶための点数としては 0 点しか出なかった。字面の比較は「答えが本文に基づくか」の確認（A5・A7 の検査）だけに使う |

## 5. 要素ごとの推論

### 5.1 共通の約束

- 依頼の形・答えの形・やり直しは既存の `element-request/v1` / `element-answer/v1` のまま。
- 1つの依頼で出させる値は1つ。指示は1〜2文。入力はその要素に必要なものだけ。
- 落ちたら **その要素だけ** を `previous_failure` 付きで再依頼。1要素 5 回まで。
- 「なし」（関係がない）は**正当な判定の答え**として受け取る。これは空の値で先へ進むこととは違う。「なし」を受けた候補は、その時点でその候補の確かめを終える（7.4）。
- 「関係の種類」の閉じた一覧（美術・市場で共通）:

| 種類 | 推論に渡す説明 |
|---|---|
| 同じ | 同じやり方・態度が両方にある |
| 逆 | 一方がすることを、もう一方は反対のやり方でする |
| 答え | 一方が抱える困りごとに、もう一方のやり方が手段を与える |
| 背景 | 一方が、もう一方の態度が生まれる時代や社会の条件になっている |

（「逆」が #280 で意味を持った対比、「答え」が #284 の補い合う、に当たる。オーナー判断 12-③）

### 5.2 A4: ふるい（窓ごとの選択）

| 項目 | 内容 |
|---|---|
| 要素 ID | `A4.art.screen.NN` / `A4.market.screen.NN` |
| 指示 | 「本人の素材と、はっきりした関係（同じ・逆・答え・背景のどれか）があるカードを1つだけ選び、番号を返してください。どれにもなければ 0 を返してください。」 |
| 入力 | `material`（3.1 の素材）、`link_types`（上の表）、`cards`（番号 → カード、最大 8） |
| 答えの形 | `choice`、`"0"`〜`"8"` |
| 確認 | 一覧にある値か（形の確認だけ。判断の中身は後段で確かめる） |
| 回数 | 窓の数だけ（美術 23、市場 9） |

窓の中のカードの並びもハッシュ順なので、「いつも1番を選ぶ」癖があっても、毎回違う項目が1番に来る。選ばれた位置の分布は記録し、受け入れ基準で見る（10章）。

### 5.3 A4: 勝ち抜き

| 項目 | 内容 |
|---|---|
| 要素 ID | `A4.art.rank.<回戦>.<組>` |
| 指示 | 「次のカードはどれも、本人の素材と関係があるとして選ばれたものです。関係が最もはっきりしていて具体的なものを1つ選んでください。」 |
| 入力 | `material`、`link_types`、`cards`（ふるいで選ばれたもの、最大 8 件ずつ。並びはハッシュ順） |
| 答えの形 | `choice`、`"1"`〜`"n"`（0 はない） |
| 確認 | 一覧にある値か |
| 回数 | 選ばれた数 P が 1 なら 0 回。2〜8 なら 1 回。9〜23 なら 組の数＋決勝 1 回（P=12 で 3 回、P=23 で 4 回） |

勝者が A5 で「なし」になったら、その勝者を除いて **勝者がいた組と決勝だけ** をもう一度行い、次の勝者を決める（約 2 回）。確かめに進む勝者は 1 領域で最大 5 人（`max_finalists: 5`）。

### 5.4 A5: 勝者の確かめ（1 勝者につき 5 要素）

| 順 | 要素 ID | 指示（要旨） | 入力 | 答えの形 | プログラムの確認 |
|---|---|---|---|---|---|
| 1 | `A5.art.<k>.type` | 本人の素材とこのカードの関係を一つ選ぶ | `material`、`card`、`link_types` | `choice`: 同じ／逆／答え／背景／なし | 一覧にある値か。「なし」ならこの勝者の確かめを終え、次の勝者へ |
| 2 | `A5.art.<k>.card-quote` | その関係の根拠になる部分を、カードの抜き書きから一字も変えずに抜く | `card_excerpts`（抜き書きだけ。名前・時代は入れない）、`link_type` | `text` 6〜80 字 | `exact_input_excerpt:card_excerpts`（一字一句一致）／名前だけ・名前の一部だけでない（`not_label`）／URL・ID・出典メモでない（`no_reference_tokens`） |
| 3 | `A5.art.<k>.self-quote` | 本人の素材の文から、その関係の根拠になる部分を一字も変えずに抜く | `material_statement`（文の行だけ）、`link_type` | `text` 4〜60 字 | `exact_input_excerpt:material_statement` |
| 4 | `A5.art.<k>.sentence` | 「<種類>」の関係を一文で書く。2つの抜き書きの言葉を使う | `self_quote`、`card_quote`、`card_label`、`link_type`（説明つき） | `text` 100 字以内 | 一文／問いの形でない／`contains_source_terms:self_quote,card_quote`／禁止語（∩、無し、未記入）／**特定性**（下記） |
| 5 | `A5.art.<k>.sentence.probe` | 次の文は、どの関係を述べていますか | `sentence_masked`（カードの名前と抜き書きを「＿＿」に置き換えた文）、`link_types` | `choice`: 同じ／逆／答え／背景 | 答えが 1 の種類と一致するか（正解はプログラムだけが持ち、依頼には入れない） |

**特定性の確認（プログラム、推論なし）**: 文の内容語（2文字以上の連続した漢字・カタカナ・英字語。既存の `source_terms`）のうち、
- 勝者のカードにあって、同じふるいの窓の他の 7 枚のどれにもない語が 1 つ以上ある
- 勝者のカードと共通の語の数が、他のどの 1 枚との共通の語の数よりも多い

の両方を満たすこと。「抽象表現主義と本人の素材は逆の関係にある」のように、どのカードにも言える文は落ちる。

**5 が一致しなかったとき**: 落ちたのは 4 の文として扱い、4 を `previous_failure`（「この文は『逆』の関係として読めませんでした。何が何に対して反対なのかを書いてください」）付きで再依頼し、通ったら 5 をもう一度行う。4 の試行は合計 5 回まで。5 自体の形の誤り（一覧にない値）は 5 だけを再依頼する。

**確かめの答え手について**: 5 は、答えを知っている答え手が答えると意味がない。Claude Code が答える場合は、会話の履歴を持たない別の作業者（サブエージェント）に渡すことを依頼に書く（`answer_context: fresh`）。ローカルモデルの adapter は依頼1件ごとに独立なので、そのままでよい。ハーネスはこれを強制できないので、記録に「誰が答えたか（answerer の種別）」を残す。

### 5.5 A6: 採用（プログラム）

- 1〜5 がすべて受理された最初の勝者を、その領域の採用とする。
- 採用しなかった勝者（「なし」になったもの）と、ふるいで選ばれたが勝者にならなかった項目は、理由つきで記録する。値を捨てて選び直すことはしない（「なし」は受理された判断であり、次の勝者は決まった手順（5.3）で出る）。

### 5.6 A7: 中心の問い（2 要素）

| 順 | 要素 ID | 指示（要旨） | 入力 | 答えの形 | 確認 |
|---|---|---|---|---|---|
| 1 | `A7.overlap` | 3つが重なるところを、平叙文の一文で書く | `material_statement`、`art_sentence`、`market_sentence` | `text` 120 字以内 | 一文／問いの形でない／`contains_source_terms:self_quote,art_card_quote,market_card_quote`（三者すべての語）／どちらのつながりの文とも似すぎない（文字2つ組の一致率 0.8 未満）／禁止語 |

### 5.7 推論の回数と上限

今のデータ（美術 179 件 → 23 窓、市場 65 件 → 9 窓、勝者の上限 5）で:

| 場合 | ふるい | 勝ち抜き | 確かめ | A7 | 合計 |
|---|---|---|---|---|---|
| 最良（選ばれたのが各1件、最初の勝者で確定、再試行なし） | 32 | 0 | 10 | 2 | **44** |
| 典型（美術 12 件・市場 5 件が選ばれ、最初の勝者で確定、再試行 1） | 32 | 3＋1 | 10＋1 | 2 | **約 50** |

- 1要素 5 回の上限に先に届いたら `BLOCKED: ELEMENT_ATTEMPTS_EXHAUSTED`。要素 ID と最後に落ちた確認の名前を添える。

## 6. 小さなモデルで「はい」「いいえ」ばかりにならない仕組み

| 起きがちなこと | 防ぎ方 | 種類 |
|---|---|---|
| 何でも「関係あり」と言う | はい/いいえ を使わず、ふるいでは「8件から1つ」、勝ち抜きでは「どれが一番か」と**比べさせる**。全部に「はい」と言うことができない形にする | 形 |
| 何でも「関係なし」と言う | 「なし」は正当な答えとして受け取り、全窓が 0 なら `NO_PICK` で止めて報告する。偽の候補で埋めない | 結果の報告 |
| いつも同じ位置を選ぶ | 窓の組み方・窓の中の並びをハッシュ順にする。位置の分布を記録して受け入れ基準で見る | プログラム |
| 関係の向きを潰す（逆なのに「同じ」） | 種類を閉じた一覧から選ばせる → 文を書かせる → 名前と抜き書きを隠した文を**別の答え手**に読ませて種類を当てさせる。一致しなければ文をやり直す | 推論＋プログラム |
| 根拠のない理由を書く | カード側・素材側とも、根拠を一字一句一致の抜き書きで出させる。名前だけ・出典メモは落とす | プログラム |
| どのカードにも言える一般的な文 | 特定性の確認（同じ窓の他の 7 枚と比べて、勝者のカードにしかない語を使っているか） | プログラム |
| 言葉の近さだけでつなぐ（「費用」と「対価」） | 完全には防げない。勝ち抜きで他の候補と比べさせることで、言葉だけの弱いつながりが勝ちにくくなる。種類の確かめで「背景」などに読み替わる場合もある。残る弱さは記録から見えるようにする | 比較＋記録 |

## 7. 決定論・再開・出所

### 7.1 決定論

- 同じ入力（signal の書き出し・commit・run の基準時刻・過去 run の使用記録）と同じ答えなら、依頼の列はバイト単位で同じになる。
- 並べ替えに使うのは sha256 だけ。種は「素材の signal_id・使用回数・項目 ID」。アルファベット順や入力ファイルの順は使わない。
- run の開始時に、素材・全カード（本文と sha256）・窓の組み方・除外の内訳・上限を **run の状態に固定** する。途中で KB の書き出しが変わっても、その run は固定した内容で最後まで進む（違う内容で再開しようとしたら今と同じく拒否）。

### 7.2 再開・並行

- 状態は既存の `element-state.json`（一つ答えるごとに原子的に保存）。どこで止まっても `next` で同じ依頼が返る。
- ふるいの窓どうし、美術と市場は互いに独立なので、将来「独立な依頼を複数まとめて出す」形にしてもよい（1依頼1値の原則は変わらない）。最初の実装では今と同じく1件ずつでよい。

### 7.3 出所（`phase-a-provenance/v2`）

研究への依頼（RR）に hash 付きで添える記録:

- 素材: signal_id、欄、文、選び方の規則と使用回数（自由文の全文を新たに作らない。書き出し済みの文だけ）
- カード: 項目 ID、抜き書き、KB の commit・locator・blob の sha256
- ふるい: 窓ごとのカード ID の並びと選ばれた番号、位置の分布
- 勝ち抜き: 回戦・組ごとの並びと勝者
- 確かめ: 種類、2つの抜き書き、つながりの文、確かめの答え、試行の履歴（落ちた確認の名前）、答え手の種別
- 採用しなかった勝者とその理由（「なし」など）
- A7: 重なりの文、中心の問い
- 推論の回数と上限

### 7.4 止まり方の一覧（理由は実際の原因と一致させる）

| 理由コード | いつ | 添えるもの |
|---|---|---|
| `SELF_EXPORT_NOT_PERMITTED` | self の書き出しがない・同意なし | — |
| `SELF_MODEL_EMPTY` | 記録が 0 件 | ヒアリングへの案内 |
| `SELF_SIGNAL_NOT_FOUND` | 指定した素材がない | 指定した ID |
| `ART_NO_ELIGIBLE_CARDS` / `MARKET_NO_ELIGIBLE_CARDS` | 候補 0 件 | 除外の内訳 |
| `CARD_SOURCE_MISMATCH` | 抜き書きが固定した本文にない | 項目 ID・locator |
| `NO_PICK:<領域>` | その領域の全窓が 0 | 窓の数・カードの数 |
| `NO_CONFIRMED_LINK:<領域>` | 勝者 5 人（または選ばれた全件）がすべて「なし」 | 各勝者の ID と答え |
| `ELEMENT_ATTEMPTS_EXHAUSTED` | 1要素が 5 回落ちた | 要素 ID・最後に落ちた確認 |
| `RUN_BUDGET_EXHAUSTED` | run の上限 | 要素ごとの回数 |
| `REQUEST_TOO_LARGE` | 1件の窓でも 4096 バイトを超える（設定の誤り） | 要素 ID |

`NO_PICK` と `NO_CONFIRMED_LINK` は「この素材では今の候補とつながらなかった」という正当な結果でもある。素材の使用回数は数え、次の run は次の素材になる（同じ run の中で素材を替えて選び直すことはしない）。

## 8. プライバシーとヒアリング

### 8.1 親（orchestration）に入るもの

- 自己モデルから親に入るのは、本人が確認し同意した**書き出し済みの文**（`approved-derived-only`）だけ。今と同じ。
- 推論の依頼に入る自己の文は、選んだ素材 1 件の文（と条件）だけ。他の記録は依頼に入れない（特定性の確認は美術・市場のカードどうしで行うので、自己側の囮はいらない）。
- 素材の抜き書き・つながりの文・重なりの文・問いは、書き出し済みの文から作られた値で、run の状態と出所の記録（Git の外、mode 0600）にだけ置く。RR からは hash 付きの URN で参照する（今の `write_request` の形）。
- `raw_voice_locator` は今どおり run の状態に残さない。

### 8.2 クラウドの答え手

素材の文はクラウドの答え手（Claude Code など）に渡る。これは #280 以来同じで、書き出しの同意の範囲（artistic-research）に含まれる前提。ローカルの答え手だけを使う設定にすれば外に出ない。

### 8.3 ヒアリングとの関係

- ヒアリングは self-model-notes の仕組み（Issue #138・#140）をそのまま中継する。親は質問・答え・依頼本文を保存しない（今の `hearing_elements.relay` の約束）。
- 質問は、オーナーが 2026-10-08 に承認した「答えを持っている問いの型」（`config/element-question-types.yaml`、revision 2、36 型）からプログラムが選び、推論はその型の言い換え一文だけを返す。段階 A は質問を作らないし、質問の選び方に口を出さない。
- 1 run につきヒアリングは最大 1 問、スキップできる。答えは本人の確認を経て次の run 以降の書き出しに出る。**その run の素材には効かない**（そう伝える文も self-model-notes の固定表のまま）。
- 段階 A がヒアリングを待つのは `SELF_MODEL_EMPTY` のときだけ。このとき self-model-notes は出来事が 3 件未満なので「出来事に頼らない型」を優先する（既存の規則）。

### 8.4 段階 A から自己モデルへ返すもの

なし。段階 A の結果（どの素材がどの項目とつながったか）を自己モデルに書き戻すと、本人が確認していない推論が自己像に入る。必要になれば、別の Issue で「本人に見せて確認する」形で設計する。

## 10. 受け入れ基準（実 run で確かめる仕組みの条件。好みの判定ではない）

1. 実データ（fixture を書き換えずに）で、`COMPLETED` になるか、7.4 のどれかの理由で止まる。止まった理由は、原因をわざと作った試験（市場を全件期限切れにする、全窓に 0 と答える、等）で、理由コードが原因と一致することを確かめる。
2. ふるいで見たカードの数が、候補の数と一致する（全件を見ている）。窓の並びが記録から再現できる。
3. 採用された 2 件とも: カードの抜き書きが固定 commit の blob に一字一句ある、A5 の抜き書きがカードに一字一句ある、素材の抜き書きが素材の文に一字一句ある、特定性の確認と種類の確かめが通っている。
4. 中心の問いが 120 字以内・一文・「？」で終わる・三者の語を含む・開いた問いである。
5. 記録した答えを新しい状態で流し直すと、依頼の列と出力がバイト単位で同じになる。任意の位置で止めて再開しても、次の依頼が同じになる。
6. 素材の回し方: 記録が N 件あるとき、続けて N 回の run で N 件すべてが 1 回ずつ使われる（合成データで確認）。
7. ふるいで選ばれた位置の分布を記録している。実 run を 3 回以上行った時点で、1 つの位置が選ばれた数の半分を超えていれば、窓の大きさか指示を見直す課題として記録する（run を止める条件にはしない）。
8. 推論の回数が上限以内で、上限をわざと小さくした試験で `RUN_BUDGET_EXHAUSTED` と内訳が出る。
9. 親の状態・ログ・出所の記録に、ヒアリングの質問・答え・raw quote・`raw_voice_locator` が入っていない（検査で確認）。
10. コードに字面の点数・操作の関係表による選択が残っていない（テストで確認）。
11. ローカルモデルの答え手で、全依頼が 4096 バイト以内で、少なくとも 1 run が `COMPLETED` または正しい理由で止まる。要素ごとの再試行数を記録する。

## 12. オーナーの決定（2026-10-10）

- 12-①〜④は推奨どおりとする: 毎回全件を見る／直近3回に採用した項目を外す／関係の種類は「同じ・逆・答え・背景」で、中心の問いは開いた問いにする／`intent` の文字列による素材選びを廃止し、ID による明示指定に置き換える。
- 答え手は、最初は LLM で全要素が動くようにして実装を完了させる。選択式の要素（ふるい・勝ち抜き・関係の種類・当てっこ）を判断モデル（Jev など）へ切り替えることは、次の課題として別 issue で扱う（並びを入れ替えた2回の答えの一致で受け取る確認を含む）。
