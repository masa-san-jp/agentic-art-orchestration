# Native-owner knowledge cycle

The pinned AAK specification and implementation plan remain the requirements authorities. This document describes the external-agent entrypoint; it does not embed a provider or authorize publication.

Start `tools/run.py --cycle-context <external-context.json> --state-root <external-state-root>`. Consume `next_action`, then execute the exact returned `resume_command` until `run_status` is terminal. The same option on `tools/autonomous_runner.py` joins this verifier after Research worker completion. Worker JSON alone only reaches `RESEARCH_COMPLETE`.

The external `knowledge-cycle-context/v1` object contains `run_id`, `instance_profile` and `local_config` paths (the AAK04 contracts), a timezone-bearing `clock`, `production_project_root`, `query_inputs`, `write_inputs`, and optional `owner_options`, `project_root`, and `project_id`. The query map has all eight owner IDs. Each value is the external JSON file containing arguments for that owner's native query. The write map has the seven writable owners, each pointing to a JSON job with exactly `action`, `inputs`, and `reason`. `action` is `write` or `no-new-evidence`; the latter has empty inputs and never fabricates a receipt or commit. Research and Production require curated writes. Project is read-only and uses catalog-reference independently of publication. When `project_root` is present, the repo-local `output-destinations/v2` resolver supplies state, internal, staging, and public roots; a v1 profile cannot silently override it.

Native input keys are listed in `tools/native_knowledge.py` and are checked before invocation. They are existing owner CLI arguments, not a shell command or copied domain schema. The adapter injects creator, collection, immutable code/knowledge commits, run ID and stable operation ID. Owners validate their own payloads and consent. Optional owner settings are the Python interpreter and Self Model `profile_root`/`subject`, or Project `catalog_root`, `catalog_repository`, `catalog_snapshot`, `catalog_collection`. Catalog collection access must be explicitly granted in the profile/local config. No remote writes occur.

The entrypoint itself must execute from the clean qualified Orchestration pin named by the profile. Bootstrap materializes each qualified code pin before native store initialization. Self Model, Marketing and Production initialize their native bare Git inside the common store container; Art History, Research, Viewer and Orchestration use the common container directly. Failed initialization uses a temporary directory and leaves the final empty store retryable. Existing stores are never reinitialized or silently adopted. All cache/query bodies remain in the corresponding owner's external store; parent state contains hashes and locators.

The agent reads the initial pinned query outputs before completing Research and the canonical handoff. Use `run.py --research-work-root` to keep native project/config/schema work outside the clean code checkout; Research's existing `--work-root`/`--protocol-root` handoff APIs retain the source pin. The agent authors the Production-owned method using the actual handoff and relevant prior conditions. The parent calls `plan_actionability.py` from qualified clean Production code and checks stable canonical bytes/assets. Missing methods return an agent action instead of PLAN_READY.

Once the plan verifies, native writes and indexes run one owner at a time. Each receipt is checked against run/owner/collection and reachable Git commits. Research/Art History use native index commands; Viewer regenerates its scoped query view. Zero-viewer evidence is adapted from the owner's NO_NEW_EVIDENCE receipt to common NO_CHANGE while retaining its meaning. Successful plan/owner checkpoints survive a later failure. On resume, native idempotent writes verify original receipts, then pinned queries are reconstructed; a saved success JSON is insufficient. Successful input changes are rejected. Owner failures and repeated no-progress calls have finite limits in `config/knowledge-cycle-runtime.json`.

Reports separate plan, knowledge, projection and run statuses. Internal delivery can complete without publication. Public delivery invokes the existing canonical projection and remains incomplete until the Project owner verifies committed receiver bytes and new creator/origin lineage; no public review or permission is inferred. A completed production run is not proof of AAK02 live acceptance: qualification additionally requires three modes with two actual external-agent runs each and inspected knowledge-adoption evidence. Synthetic regressions never qualify as live acceptance.

Project's read-only catalog query may return `BLOCKED` when a pre-existing
record deliberately remains `UNKNOWN_ATTRIBUTION`. The cycle retains that
status and blocker count in the query evidence; it never treats the record as
validated, changes its attribution, or uses it as lineage. An unrelated new
plan may continue only if its own automatic attestation, native Project
lineage initialization, and local receiver validation all pass.

The legacy purpose E2E `live-private` name describes data access, not proof of an actual LLM worker. Its historical evidence remains readable; new supervisor records say RESEARCH_COMPLETE. Only the separately recorded AAK02 actual-agent matrix can satisfy live acceptance.

Initial searches retain the supplied snapshot clock. Each native write captures its own actual clock before invocation and retains it with the operation/job hash; retries and post-write queries reuse that clock. This permits observations obtained during Research without falsely treating them as future observations or changing the original read snapshot.

## Requested delivery completion (Issue 217)

For a request to output to Project, run `tools/run.py --cycle-context <external-context.json> --project-root <project-checkout> --state-root <project-checkout>/.agentic-art/state --delivery-target project-local`. The context/profile must explicitly authorize public-catalog projection and select the Project root; an internal profile mismatch is an error, never silent SKIPPED success. The saved context records `project_root`, `delivery_contract: {contract_version: delivery-contract/v1, target: project-local}`, the repo-local `destination-resolution/v2` in run state, and the exact resume command. Legacy contexts keep their existing internal/committed-catalog semantics; no profile is silently migrated.

Continue the returned agent actions through Production plan generation, the closed automatic plan attestation, canonical projection, native Project lineage initialization and local receiver validation. The automatic plan lane performs Production's renderer, content, asset and provenance checks and records `publication_review.authority: AUTOMATIC_PLAN`; it never waits for human approval and never authorizes an external effect. Work/manual requests use the separate native review lane. If an automatic check fails, the agent receives the exact repair finding and resumes the same run. Run the native runtime bootstrap when a freshly built plan has not yet initialized its event log. Do not fabricate approvals. A human wait applies only to a separately requested work/manual publication and does not consume the no-progress retry budget.

`PLAN_READY` and batch `PASSED` describe stages, not final delivery. For the cycle entry, only `delivery_completion.status=COMPLETED` with the requested target is the overall completion report. Required knowledge saves, receiver hashes and creator/origin must verify. A local receipt does not prove Git commit or remote synchronization. GitHub Actions, account billing and a built-in provider are not required. Existing AAK internal evidence is not public-catalog acceptance.
